# <img width="30" height="30" alt="image" src="https://github.com/user-attachments/assets/9cd1343f-3b3a-47c7-a9a4-ab92b6e2bb91" /> SourceTrail MCP 3.1.0

C# WinForms의 화면·이벤트에서 서비스와 DB 호출 위치를 찾고, 로컬 SQL 파일에서 프로시저 정의와 직접 참조를 확인하는 MCP 서버입니다. 파일·줄 번호를 근거로 **MCP로 위치 찾기 → 원문에서 실제 이름 확인 → 그 이름으로 MCP 재검색** 순서로 사용합니다.

PC에 **서버 하나**를 두고 Claude Code의 여러 대화와 Codex가 같은 프로세스와 메모리 색인을 함께 씁니다. 클라이언트에는 가벼운 **브리지**(`--bridge`)를 등록하면, 클라이언트를 열 때 서버가 켜지고 모든 클라이언트를 닫으면 10분 뒤 서버가 꺼집니다. 서버를 계속 띄워 두고 주소(`http://127.0.0.1:3920/mcp`)로 접속하거나, 클라이언트마다 따로 실행하는 `--stdio`도 사용할 수 있습니다. 2.x의 stdio 등록은 그대로 두면 연결되지 않으므로 [2.x에서 옮기기](docs/http-server.md#2x에서-옮기기)를 확인하세요.

C# 구문 파서를 사용하며 컴파일·MSBuild·참조 DLL 로딩은 하지 않습니다. DB는 `SqlFiles`만 지원하고 SQL Server에 접속하지 않습니다. 검색은 원본을 읽고, 색인 준비·갱신은 로컬 캐시만 저장합니다. 반환된 이름·Adapter 매핑은 정적 후보이므로 실제 연결과 조건은 원문으로 확인합니다.

## AI 도구에 설치 맡기기

아래 프롬프트를 Windows의 Codex 또는 Claude Code에 붙여넣으세요. SourceTrail은 로컬 HTTP(streamable HTTP) MCP를 지원하는 클라이언트에서 사용할 수 있으며, stdio만 지원하는 클라이언트는 `--stdio`로 등록합니다. 소스와 SQL 경로는 자신의 경로로 채웁니다. 비워 두면 설치 에이전트가 확인하도록 되어 있습니다. `.sln` 없이 소스 폴더를 지정해도 됩니다.

```text
이 Windows PC에 SourceTrail MCP를 설치하고 현재 사용 중인 MCP 클라이언트에 등록해줘.
저장소: https://github.com/shc6260/SourceTrail
설명에서 멈추지 말고, 확인된 경로와 아래 절차로 설치를 진행해줘.

C# 소스 경로(.sln 파일 또는 소스 폴더):
SQL 스크립트 폴더(.sql 파일이 있는 폴더):

1. 비어 있거나 예시 값인 경로는 사용자에게 확인한다. 답을 받기 전에 추정하지 않는다.
   소스 폴더는 .sln 없이 그대로 사용할 수 있다. 파일·폴더가 실제로 읽히는지 확인한다.
2. 기존 SourceTrail 등록과 체크아웃을 확인한다. 없으면 사용자 폴더에 저장소를 복제한다.
   기존 변경사항은 덮어쓰지 않는다. Git과 .NET 10 SDK가 없으면 공식 배포본으로 설치하고
   권한 승인이 필요한 경우에만 알린다.
   rg.exe/rg가 있으면 실제 실행 경로를 확인한다. 없으면 기존 .NET 텍스트 검색으로
   동작하므로 설치 실패로 처리하지 않고 검색 엔진 상태를 결과에 알린다.
3. 저장소에서 아래 명령으로 publish하고 실행 DLL의 절대 경로를 확인한다.
   dotnet publish src/SourceTrail.Mcp/SourceTrail.Mcp.csproj -c Release -o artifacts/server
   실행에는 publish 폴더 전체를 보관한다. 분석 대상 프로젝트의 컴파일·빌드는 하지 않는다.
4. 일괄 색인 저장소를 정한다. 기본은 실제 MCP 실행 사용자의
   %LOCALAPPDATA%\SourceTrail\prepared-index이며 실제 절대 경로로 확정한다.
   기존에 지정한 저장소가 있으면 유지한다. 클라이언트의 프로젝트 폴더에 임의로 만들지 않는다.
5. 최초 일괄 색인을 생성한다.
   dotnet <실행 DLL 절대 경로> prepare-index --source <확인한 C# 경로>
     --sql-folder <확인한 SQL 폴더> --index-directory <확정한 색인 저장소>
   위 인수는 한 명령에 전달하고 공백을 포함한 경로는 인용한다.
   기존 C#·SQL 캐시 설정이 있으면 명령에도 같은 설정이나 환경변수로 전달한다.
   기본 증분 모드를 사용한다. 사용자가 전체 재생성을 명시한 경우에만 --rebuild를 붙인다.
   기존 색인을 먼저 지우지 않는다. 종료 코드 0과 Published=true를 확인한다.
   생성·재사용 건수, 구문 진단·SQL 경고, 단계별 시간을 기록한다.
   실패하면 설치 완료로 보고하지 않는다.
6. README의 "서버 실행과 클라이언트 등록"에 따라 서버를 설정한다.
   publish 폴더의 SourceTrail.Mcp.dll 옆 appsettings.json에 서버 설정을 둔다.
   Analysis.SolutionPath, Database.SqlFolder는 준비에 사용한 경로와 같게 설정한다.
   Database.Mode=SqlFiles, Indexing.Directory는 4~5번과 같은 절대 경로를 사용한다.
   신규 설치 권장값은 Analysis.WatchCodeFiles=true, Analysis.CodeRescanIntervalSeconds=30이다.
   rg 경로를 확인했으면 Analysis.RipgrepPath에 지정한다. 사용자가 명시한 기존 설정은 유지한다.
   Server.Url 기본값 http://127.0.0.1:3920을 사용하고 루프백이 아닌 주소는 쓰지 않는다.
   포트가 이미 사용 중이면 사용자에게 알리고 다른 포트를 정한다.
   서버 실행용 작업 스케줄러 작업은 직접 등록하지 않는다. 브리지가 처음 서버를 켤 때
   현재 사용자 권한으로 'SourceTrail MCP' 작업(트리거 없음, 창 없는 SourceTrail.Launcher.exe 실행)을
   자동 등록한다. PC 설정에 남는 변경이므로 사용자에게 알린다.
7. docs/mcp-registration.md에서 현재 클라이언트의 절차에 따라
   sourcetrail을 브리지로 등록한다: command는 dotnet, args는 SourceTrail.Mcp.dll 절대 경로와 --bridge.
   서버 설정용 환경변수는 클라이언트 등록에 넣지 않는다. 다른 클라이언트 설정은 변경하지 않는다.
   연결 대기 60초·도구 대기 300초를 신규 권장값으로 사용하고 기존 값은 유지한다.
   대기 시간은 클라이언트별 지원 방식으로 설정한다. Codex 전용 설정 키를
   다른 클라이언트에 복사하지 않는다. 지원 여부를 확인하지 못하면 확인 필요로 남긴다.
   사용자가 서버를 계속 띄워 두길 원하면 HTTP 주소 등록, 공유 없이 쓰길 원하면 --stdio를 사용한다.
   다른 MCP 등록을 변경하지 않고 sourcetrail을 중복 등록하지 않는다.
8. MCP를 새로 연결하고 ping의 pong을 확인한다.
   설정된 소스에서 실제로 확인한 식별자로 선언 검색을 한 번 수행하고,
   실제 SQL 파일에서 확인한 객체명으로 find_sql_object를 호출한다.
   상태·대상 경로·파일 수·주요 진단을 확인한다.
   일괄 준비가 성공했으면 검증을 위해 전체 재생성이나 refresh를 반복하지 않는다.
   현재 대화에 도구가 보이지 않으면 등록 완료와 실제 호출 검증 여부를 구분하고
   재연결이 필요하다고 설명한다.

설치 결과를 표로 정리해줘:
- 저장소·실행 DLL 위치
- 서버 주소·서버 설정 파일·서버 실행용 작업 등록 여부
- 사용한 MCP 클라이언트·설정 파일·등록 범위와 등록 방식(브리지 실행 명령 또는 주소)
- C#·SQL 분석 대상
- 일괄 색인 저장소, 활성 세대, 생성·재사용 건수와 주요 경고
- 변경 감지 설정과 연결·호출 대기 시간
- 연결 및 실제 검색 검증 결과

확인 못 한 내용은 확인 필요로 표시한다.
원본 소스·SQL은 수정하지 않고, SQL Server 접속·SQL 실행·운영 반영은 하지 않는다.
```

### 설치 기본값과 저장 위치

| 항목 | 기본·권장값 |
|---|---|
| 실행 방식 | 클라이언트는 브리지(`dotnet …SourceTrail.Mcp.dll --bridge`) 등록. 브리지가 공유 서버 `http://127.0.0.1:3920/mcp`를 필요할 때 켜고, 연결된 브리지가 없으면 10분 뒤 서버 종료. 루프백만 허용 |
| 서버 설정 | DLL 옆 `appsettings.json`. 서버와 브리지가 같은 파일을 읽으며 클라이언트 등록에는 환경변수를 넣지 않음 |
| 분석 대상 | 확인한 절대 소스 폴더 또는 `.sln`, 로컬 SQL 폴더 |
| 일괄 색인 | `%LOCALAPPDATA%\SourceTrail\prepared-index` |
| 활성 세대가 없을 때 C# 캐시 | `Analysis.CodeCacheDirectory`. 빈 값이면 C# 디스크 재사용 비활성화 |
| 활성 세대가 없을 때 SQL 캐시 | `%LOCALAPPDATA%\SourceTrail\cache` |
| 변경 확인 | 설치 프롬프트·배포 예제는 `WatchCodeFiles=true`, 30초 주기. 설정 생략 시 라이브러리 기본은 `false` |
| 텍스트 검색 | `Analysis.UseRipgrep=true` 기본. PATH의 `rg.exe`/`rg` 또는 `Analysis.RipgrepPath` 사용. 없거나 실패하면 기존 .NET 검색으로 대체 |
| 연결·도구 대기 | 신규 설치 권장 30초·300초 |

일괄 색인은 MCP 클라이언트의 프로젝트 폴더와 별개입니다. **어떤 클라이언트 프로젝트를 열었는지가 아니라 MCP에 설정된 소스·SQL 경로를 따릅니다.** 저장소 하나에는 활성 세대 하나가 있고, 소스·SQL 경로가 모두 일치할 때 해당 세대의 캐시를 사용합니다. 여러 분석 대상을 각각 유지하려면 저장소와 MCP 설정을 분리하세요. 클라이언트 프로젝트별 자동 분리 기능은 없습니다.

설정은 실행 DLL 옆 `appsettings.json` 또는 환경변수로 지정합니다. HTTP 상주 서버는 서버를 실행하는 환경의 환경변수를, stdio는 클라이언트 등록의 환경변수를 읽습니다. 환경변수가 JSON보다 우선합니다. `Indexing.Directory`를 생략하면 기본 저장소를 사용하며, 별도 경로를 지정하면 준비 명령과 MCP 설정을 동일하게 맞춰야 합니다. 활성 세대가 일치하면 그 안의 C#·SQL 캐시가 개별 캐시 경로보다 우선합니다.

## 서버 실행과 클라이언트 등록

SourceTrail은 PC에 **서버 하나**를 두고 여러 클라이언트가 함께 쓰는 방식입니다. Claude Code의 여러 대화, Codex, 스크립트 작업자가 같은 프로세스와 메모리 색인을 사용하므로 색인 로딩은 서버가 뜬 뒤 첫 조회 한 번뿐입니다. 권장 방식은 **브리지 등록**입니다. 클라이언트를 열면 서버가 켜지고, 모든 클라이언트를 닫으면 잠시 뒤 서버가 꺼집니다.

```text
Claude 대화 1 ── 브리지(stdio) ─┐
Claude 대화 2 ── 브리지(stdio) ─┼─ http://127.0.0.1:3920/mcp ─→ SourceTrail 서버 1개 (색인 공유)
Codex        ── 브리지(stdio) ─┘
```

| 방식 | 클라이언트 등록 | 서버가 켜지는 때 | 서버가 꺼지는 때 |
|---|---|---|---|
| **브리지 (권장)** | `dotnet …\SourceTrail.Mcp.dll --bridge` | 브리지를 쓰는 클라이언트를 처음 열 때 | 연결된 브리지가 하나도 없는 상태가 10분 이어지면 |
| HTTP 상주 | 주소 `http://127.0.0.1:3920/mcp` | 직접 실행하거나 로그인 시 자동 실행 | 직접 끌 때까지 |
| 단독 stdio | `dotnet …\SourceTrail.Mcp.dll --stdio` | 클라이언트·대화마다 따로 | 그 클라이언트가 끝날 때 (공유 없음) |

### 1. 서버 설정

publish 폴더의 `SourceTrail.Mcp.dll` 옆에 `appsettings.json`을 둡니다. [appsettings.example.json](src/SourceTrail.Mcp/appsettings.example.json)을 복사해 경로를 채우세요. 분석 대상은 서버 설정에서만 지정하며 브리지도 같은 파일을 읽습니다.

```json
{
  "Server": { "Url": "http://127.0.0.1:3920", "Path": "/mcp" },
  "Analysis": { "SolutionPath": "D:\\Projects\\Sample\\Sample.sln", "WatchCodeFiles": true, "CodeRescanIntervalSeconds": 30 },
  "Database": { "Mode": "SqlFiles", "SqlFolder": "D:\\Projects\\Sample\\DatabaseScripts" },
  "Indexing": { "Directory": "C:\\Users\\<사용자>\\AppData\\Local\\SourceTrail\\prepared-index" }
}
```

### 2. 서버 실행용 작업 (Windows, 자동 등록)

따로 등록할 필요가 없습니다. 브리지는 작업 스케줄러의 `SourceTrail MCP` 작업으로 서버를 켜며, 작업이 없으면 처음 서버를 켤 때 현재 사용자 권한으로 자동 등록합니다(관리자 권한 불필요, 트리거 없음). 이렇게 켠 서버는 클라이언트의 프로세스 묶음 밖에서 실행되므로, 서버를 켠 대화를 닫아도 다른 대화가 계속 사용할 수 있습니다.

- 작업은 publish 폴더의 `SourceTrail.Launcher.exe`를 실행합니다. 창 없는 실행기이므로 기본 터미널 설정과 관계없이 **콘솔 창이 뜨지 않습니다.**
- 브리지가 등록한 작업은 새 폴더에 publish하면 다음 서버 시작 때 실행 경로가 자동으로 바뀝니다.
- 손으로 등록한 같은 이름의 작업은 바꾸지 않고 그대로 실행합니다. 3.1 이전 방식(`dotnet …dll` 실행)으로 등록한 작업은 서버가 켜질 때 창이 뜨므로 지우고 브리지가 다시 등록하게 하세요: `Unregister-ScheduledTask -TaskName 'SourceTrail MCP' -Confirm:$false`
- 작업 스케줄러를 쓸 수 없으면 브리지가 실행기로 서버를 직접 켭니다. 창은 뜨지 않지만, 클라이언트가 프로세스 트리 전체를 종료하면 서버도 함께 종료될 수 있습니다.

### 3. 클라이언트 등록 (브리지)

| 클라이언트 | 등록 |
|---|---|
| Codex | `~/.codex/config.toml`에 `[mcp_servers.sourcetrail]`, `command = "dotnet"`, `args = ['D:\Tools\SourceTrail\artifacts\server\SourceTrail.Mcp.dll', '--bridge']`, `startup_timeout_sec = 60`, `tool_timeout_sec = 300` |
| Claude Code | 프로젝트 `.mcp.json`에 `{"type": "stdio", "command": "dotnet", "args": ["D:\\Tools\\SourceTrail\\artifacts\\server\\SourceTrail.Mcp.dll", "--bridge"], "timeout": 300000}` 또는 `claude mcp add --transport stdio --scope user sourcetrail -- dotnet 'D:\Tools\SourceTrail\artifacts\server\SourceTrail.Mcp.dll' --bridge` |

등록에는 서버 설정용 환경변수를 넣지 않습니다. 등록 후 클라이언트를 다시 연결하고 `ping`이 `pong`을 반환하는지 확인합니다. 자세한 예시는 [MCP 등록 및 설정](docs/mcp-registration.md)에 있습니다.

### 알아둘 점

- **자동 종료는 연결된 브리지를 기준으로 합니다.** 브리지는 30초마다 연결 신호를 보내고, 서버는 90초 넘게 신호가 없는 브리지를 끊어진 것으로 봅니다. 대화를 열어 두면 쓰지 않아도 서버는 켜져 있습니다. 주소로 직접 등록한 클라이언트는 자동 종료 판단에 포함되지 않으므로, 자동 종료 서버를 쓸 때는 모든 클라이언트를 브리지로 등록하세요.
- **서버가 도중에 꺼져도 다음 호출에서 브리지가 다시 켭니다.** 다시 켠 뒤에는 첫 조회에서 색인을 다시 메모리에 올립니다.
- **이 PC에서만 접속할 수 있습니다.** 서버 주소는 루프백(127.0.0.1, localhost, [::1])만 허용하며 다른 주소면 서버가 시작하지 않습니다. 인증은 없으므로 같은 PC의 다른 프로세스는 접속할 수 있습니다.
- **호출은 한 번에 하나씩 처리합니다.** 결과가 섞이지 않는 대신, 다른 클라이언트의 긴 호출(예: 서버 시작 직후 첫 전체 문자열 검색)이 끝날 때까지 기다릴 수 있습니다.
- **분석 대상을 바꾸려면 서버 설정을 바꾸고 서버를 다시 시작합니다.** 한 클라이언트가 대상을 바꾸면 모든 클라이언트에 영향이 가므로 `load_solution`·`select_database_source`는 기본 차단입니다.
- **서버를 다시 시작해야 하는 경우:** 분석 대상·캐시 경로 변경, 새 색인 세대 게시(`prepare-index`), 새 버전 publish. 실행 중인 `SourceTrail.Mcp.exe --http` 프로세스(이전 방식은 `dotnet …SourceTrail.Mcp.dll --http`)를 끄면 다음 호출에서 브리지가 새로 켭니다.
- **계속 켜 두려면** 작업에 로그인 트리거를 추가하고 `--Server:AutoShutdown=true`를 빼거나, 클라이언트를 주소로 등록합니다.
- **2.x에서 올릴 때:** 기존 stdio 등록은 `--bridge`(권장) 또는 `--stdio`를 붙여야 연결됩니다.

설정 항목 전체, 상태 확인·중지 방법, 동작 원리는 [HTTP 서버와 브리지](docs/http-server.md)를 참고하세요.


## 기존 설치 업데이트

이미 설치했다면 아래 프롬프트를 사용하세요. **사용 지침 MD만 바뀌면 저장소 갱신으로 충분**합니다. 프로젝트가 같은 로컬 MD 경로를 참조한다면 링크를 다시 추가할 필요가 없습니다. 프로그램이 바뀐 경우에는 새 실행 폴더에 publish한 뒤 클라이언트 등록의 DLL 경로를 바꾸고 실행 중인 서버를 끕니다(브리지가 등록한 서버 실행용 작업은 자동으로 새 폴더를 가리킵니다). 다음 호출에서 브리지가 새 서버를 켭니다. 업데이트마다 전체 색인을 재생성하지 않습니다. **2.x에서 올릴 때는 실행 방식이 바뀌므로** [2.x에서 옮기기](docs/http-server.md#2x에서-옮기기)를 따릅니다.

```text
이 PC의 기존 SourceTrail MCP를 GitHub 최신 master 기준으로 업데이트해줘.
저장소: https://github.com/shc6260/SourceTrail
아래 절차로 진행하고 결과는 채팅에 간단히 알려줘. 별도 보고서는 만들지 않는다.

1. 기존 체크아웃·커밋과 등록된 실행 DLL을 확인한다.
   소스·SQL 경로, appsettings.json과 MCP 환경변수, 색인·캐시 경로,
   변경 감지·대기 설정 및 사용 지침 MD 참조 위치를 확인한다.
   인증정보를 답변·로그에 출력하지 않는다. 기존 실행 경로와 설정을 복구할 수 있게 보존한다.
2. 원격 master를 fetch하고 현재 커밋과 변경 범위를 비교한다.
   로컬 변경·분기된 이력은 덮어쓰거나 임의 reset/stash하지 않는다.
   문제가 없으면 fast-forward로 갱신한다. 충돌이 있으면 상태와 선택지를 설명하고 묻는다.
3. 문서만 변경됐다면 프로그램 publish·서버 재시작·MCP 재연결·색인 생성은 생략한다.
   기존 프로젝트 지침의 MD 링크가 유효한지 확인한다.
   실제 사용 지침 문서가 읽히는 경로를 유지하고, 복사본을 쓰는 환경은
   사용자 작성 규칙을 보존하면서 SourceTrail 부분만 갱신한다.
4. 프로그램 또는 빌드 입력이 변경됐다면 실행 중인 폴더를 덮어쓰지 않고
   별도 새 폴더에 다음 명령으로 publish한다.
   dotnet publish src/SourceTrail.Mcp/SourceTrail.Mcp.csproj -c Release -o <새 실행 폴더>
   기존 appsettings.json의 사용자 설정과 MCP 환경변수를 새 버전에서 대조한다.
   소스·SQL·색인·캐시·변경 감지·대기 설정을 유지하고 새 기본값으로 덮어쓰지 않는다.
   폐기되거나 호환되지 않는 설정은 영향과 필요한 변경을 먼저 설명한다.
5. 기존 색인은 삭제하지 않고 재사용한다. 업데이트만을 이유로 prepare-index,
   --rebuild 또는 refresh를 실행하지 않는다. 캐시 형식 변경 등으로 준비가 실제로
   필요하면 이유를 확인하고 증분 준비를 우선한다. 기존 버전의 복구용 색인도 보존한다.
6. publish 성공 후 실행 경로를 새 폴더로 전환한다.
   기존 서버 설정(appsettings.json)을 새 폴더로 옮기고, 클라이언트 등록의
   DLL 경로를 바꾼 뒤 실행 중인 서버(--http)를 멈춘다. 브리지가 등록한 서버 실행용 작업은
   다음 서버 시작 때 새 폴더로 자동 갱신된다. 손으로 등록한 작업('dotnet …dll' 실행)이면
   사용자에게 알리고 삭제해 브리지가 창 없는 작업으로 다시 등록하게 한다. 브리지 등록은 --bridge를, 단독 stdio 등록은 --stdio를 유지한다.
   주소로 등록한 클라이언트는 주소가 같으면 바꾸지 않는다.
   2.x stdio 등록을 올리는 경우: 브리지 전환(권장), HTTP 주소 등록, args에 --stdio 추가 중
   무엇을 할지 사용자에게 먼저 묻는다. 그대로 두면 연결되지 않는다.
   다른 MCP 등록은 변경하지 않고 중복 등록하지 않는다.
   ping과 기존 분석 대상의 C# 선언 검색·SQL 객체 조회를 확인한다.
   현재 대화에서 재연결할 수 없으면 '전환 완료·검증 대기'로 구분하고
   필요한 재연결 방법을 알려준다. 검증 없이 업데이트 성공으로 단정하지 않는다.
7. 새 버전 검증에 실패하면 이전 DLL 경로·설정으로 되돌려 서버를 다시 시작(또는 재연결)하고 복구를 확인한다.
   검증이 끝나기 전에는 이전 실행 폴더·복구용 설정·색인을 삭제하지 않는다.

결과: 이전/이후 커밋, 문서만 갱신했는지 프로그램도 교체했는지,
현재 실행 DLL·MD 경로, 유지·변경한 설정, 색인 재사용 여부,
검색 검증 결과와 남은 확인 필요사항을 간단히 알려줘.
분석 대상 원본 소스·SQL 수정, 대상 프로젝트 빌드, DB 접속·SQL 실행은 하지 않는다.
```

## 프로젝트에 사용 지침 적용

설치 후 **실제로 분석할 프로젝트**의 지침에 아래 내용을 추가하세요. Codex는 `AGENTS.md`, Claude Code는 `CLAUDE.md`, 다른 클라이언트는 해당 도구가 읽는 프로젝트 지침을 사용합니다. 이미 공통 지침을 참조한다면 그 공통 문서에 한 번만 추가하면 됩니다.

아래 `D:/Tools/SourceTrail`은 예시입니다. 설치한 SourceTrail 저장소의 실제 절대 경로로 바꾸세요. MCP 등록만으로 이 MD가 자동 적용되지는 않습니다.

```markdown
## SourceTrail 사용

- SourceTrail을 사용하는 조사에서는 [상세 사용 지침](D:/Tools/SourceTrail/docs/usage-guidelines.md)을 먼저 읽는다.
- MCP 후보 → 필요한 원문에서 실제 이름·계약·인수 확인 → MCP 재조회 순서로 진행한다. 질문에 맞는 도구를 선택하고 확보한 근거를 재사용한다.
- 요청한 근거를 확보하면 종료한다. 추가 사용처 조사나 범위·방식 변경은 먼저 묻는다. 결과는 채팅에 간단히 답하며 보고서 파일·상세 계측은 요청할 때만 작성한다.
- 기존 프로젝트의 역할·쓰기·DB 접근 제한을 유지한다.
```

경로에 공백이 있으면 링크 대상을 `<D:/설치 경로/SourceTrail/docs/usage-guidelines.md>`처럼 꺾쇠로 감싸세요. 도구별 규칙과 자세한 설명은 [상세 사용 지침](docs/usage-guidelines.md)에 있습니다.

## 실행·검색 순서

### 설치할 때

```text
소스·SQL 경로 확인 → publish → 최초 일괄 색인 생성 → 파일로 저장
→ 서버 설정·서버 실행용 작업 등록 → 클라이언트에 브리지 등록 → 연결 → 실제 검색 검증
```

### 서버를 시작할 때

```text
클라이언트가 브리지 실행 → 브리지가 서버 확인, 없으면 작업 스케줄러로 서버 실행
→ 서버가 설정 읽기 → 분석 경로와 일치하는 활성 색인 선택 → 127.0.0.1에서 요청 대기
→ 연결된 브리지가 모두 끝나고 10분 지나면 서버 종료
```

일괄 색인이 있어도 시작 즉시 모든 내용을 메모리에 읽지는 않습니다. 서버가 받은 첫 관련 요청에서 파일 목록·캐시를 확인하고 필요한 색인을 메모리에 올립니다. 이후에는 어느 클라이언트의 요청이든 같은 메모리 색인을 재사용합니다.

```text
첫 C# 선언 요청 → 파일 목록·메타데이터 대조 → 저장된 선언 재사용
첫 UI 요청      → UI 입력 메타데이터 대조 → UI 캐시 로딩 또는 생성
첫 SQL 요청     → 저장된 SQL 캐시 로딩 → 목록·메타데이터 대조 → 변경분 갱신
```

일괄 색인을 아직 만들지 않았다면 필요한 요청 시점에 준비합니다. C#은 파일 목록을 먼저 만들고 필요한 선언을 구문 분석하며, SQL은 지정 폴더의 정의를 색인합니다. UI는 별도 색인을 사용합니다.

### 실행 중 계속 사용할 때

```text
요청 → 메모리 색인 재사용 → 필요한 위치·후보 반환
변경 알림 또는 대조 주기 경과 → 다음 요청에서 변경 확인·갱신 → 응답
```

C# 감시 모드와 SQL 감시는 알림·주기를 사용합니다. UI는 조회 시 입력 메타데이터의 fingerprint를 비교하고, 바뀌면 UI 색인을 다시 만듭니다. 감시 알림 전달 전에는 짧은 지연이 있을 수 있고, 감시 오류 시 전체 대조로 복귀합니다. 요청마다 C#을 대조해야 하면 `WatchCodeFiles=false`를 사용합니다.

### 실제 코드 조사를 할 때

```text
사용자 지시 → MCP로 후보 위치 찾기 → 핸들러·관련 메서드 원문 읽기
→ 실제 호출명·계약·인수 확인 → 그 이름으로 MCP 재검색
→ 필요한 다음 연결만 반복 → 확인된 프로시저의 SQL 정의 확인 → 보고
```

MCP는 위치와 후보를 찾습니다. 원문의 호출 관계·조건 분기·인수·행 상태를 대조하는 작업이 필요합니다. 원문에서 연결을 확인했다면 같은 연결을 전체 사용처 검색으로 다시 검증할 필요는 없습니다.

## 일괄 색인 생성·갱신

C# 선언 → WinForms UI → SQL 정의·직접 참조를 미리 분석해 로컬 파일에 저장합니다. 컴파일러·MSBuild·DB 연결은 사용하지 않습니다. 준비 비용을 설치·갱신 단계로 옮기는 기능이며 첫 메모리 로딩 비용까지 없어지는 것은 아닙니다.

### CLI

publish 후 PowerShell에서 실행합니다. 아래 소스·SQL 경로는 자신의 경로로 바꾸세요.

```powershell
$preparedIndex = Join-Path ([Environment]::GetFolderPath('LocalApplicationData')) 'SourceTrail\prepared-index'
dotnet .\artifacts\server\SourceTrail.Mcp.dll prepare-index `
  --source 'D:\Projects\Sample\Sample.sln' `
  --sql-folder 'D:\Projects\Sample\DatabaseScripts' `
  --index-directory $preparedIndex
```

DLL 옆 설정이나 환경변수에 대상과 저장소가 지정돼 있다면 다음처럼 실행할 수도 있습니다.

```powershell
dotnet .\artifacts\server\SourceTrail.Mcp.dll prepare-index
```

| 요청 | 동작 |
|---|---|
| `prepare-index` | 기존 결과를 재사용하며 변경·추가 파일을 분석하고 삭제 파일을 제외 |
| 같은 명령에 `--rebuild` 추가 | 기존 캐시를 사용하지 않고 전체 재생성 |
| MCP `prepare_indexes`에 `{}` | 설정된 경로로 일괄 생성·증분 갱신 |
| MCP `prepare_indexes`에 `{"rebuild":true}` | 설정된 경로로 전체 재생성 |

C#·SQL의 메타데이터가 같으면 캐시를 재사용합니다. SQL은 변경 파일의 내용 해시를 비교해 실제 내용이 달라진 파일만 다시 파싱합니다. UI 입력이 달라지면 UI 색인 전체를 다시 생성합니다. 크기·시각을 모두 유지한 오프라인 수정은 메타데이터만으로 구분하지 못할 수 있으므로 전체 재생성으로 확인할 수 있습니다.

### 완료·실패와 서버 재시작

```text
별도 작업 세대에 생성 → 입력 변경 여부 재확인 → 완료된 세대를 활성화
실패·취소 → 기존 활성 색인 유지 → 이번 미완료 작업만 정리
```

결과에는 `Published`, 생성·재사용 건수, 구문 진단·SQL 경고, 단계별 시간이 나옵니다. CLI 종료 코드는 완료 0, 실패 1, 취소 130입니다. `Published=true`여도 구문 진단이나 SQL `Partial` 경고를 확인해야 합니다. 모든 객체나 실행 관계의 완전성을 뜻하지 않습니다.

기존 활성 색인을 먼저 지우지 않습니다. 이전 세대는 실행 중인 MCP가 참조할 수 있어 자동 삭제하지 않으며, 재생성에는 추가 디스크 공간이 필요합니다. **새 세대를 사용하려면 HTTP 서버를 다시 시작합니다(stdio는 MCP 재연결). 재시작·재연결 때문에 색인을 다시 만들 필요는 없습니다.**

원본 SQL 정의와 소스 선언이 캐시에 포함되므로 로컬 캐시를 공개 저장소에 올리지 마세요. 큰 프로젝트에서는 선언 캐시의 크기·메모리 로딩 비용이 커질 수 있습니다. [세부 동작과 반환값](docs/index-preparation.md)

## 효율적으로 사용하는 프롬프트

질문별 시작 도구와 중복 조회 방지 규칙은 [상세 사용 지침](docs/usage-guidelines.md)을 참고하세요. 프로젝트 지침에는 해당 문서의 링크와 핵심 규칙만 두면 됩니다.

아래는 실제 조사용 프롬프트입니다. 시작할 때 조사 범위를 고정하고, 원문에서 확인한 이름으로만 다음 연결을 찾습니다. 이름을 알고 있으면 전체 이름과 알려진 폴더로 범위를 좁히세요. 이 프롬프트가 특정 응답시간을 보장하는 것은 아닙니다.

```text
SourceTrail 2.0으로 접수 저장 로직을 찾아줘.

대상은 MCP에 설정된 C# 소스와 로컬 SQL 폴더(SqlFiles)를 사용한다.
주요 접수정보·접수항목의 개별/일괄 저장, Added/Modified/Deleted 및 후처리를 확인한다.
별도 화면·예약·외부연동·출력과 SQL 내부 호출의 재귀 추적은 제외한다.

1. find_ui_actions에 "접수 저장"을 전달한다.
   버튼 문구와 이벤트 원문으로 신규 접수·수정 버튼을 구분한다.
2. 후보의 핸들러와 저장 메서드 원문을 읽어 실제 호출명·계약·인수를 확인한다.
   이름을 추정해서 먼저 검색하지 않는다.
3. 확인한 식별자·전체 이름으로 find_symbol 또는 범위를 좁힌 search_text를 사용한다.
   반환된 소스 ID는 추정·재작성하지 말고 그대로 다음 도구에 전달한다.
   알려진 C# 절대 경로는 get_symbol_overview에 사용할 수 있다.
4. find_database_calls는 현재 메서드 하나만 조회한다. symbol과 limit을 사용하고
   methodCandidates와 원문에서 필요한 다음 연결만 골라 같은 순서로 이어간다.
   maxDepth/maxMethods와 자동 전체 그래프 도구는 사용하지 않는다.
5. 실제 WCF 계약, 인수 타입, 조건부 분기, 행 상태와 개별/일괄 방식을 원문으로 대조한다.
   CommandText 설정·Adapter 매핑만으로 실제 실행을 단정하지 않는다.
6. 연결을 원문으로 확인한 프로시저만 find_sql_object/analyze_procedure로 확인한다.
   위치만 필요하면 locationsOnly=true, 본문 분석이 필요하면 정의와 직접 참조를 조회한다.

조회 규칙:
- search_text에는 확인한 코드 문자열과 알려진 directory·허용 extension을 사용한다.
- 원문은 필요한 구간만 읽고 이미 읽은 같은 내용은 재사용한다.
- 이미 확인한 연결을 전체 이름 사용처 검색으로 재검증하지 않는다.
- find_reference_candidates 등 추가 사용처 조사가 필요하면 목적·범위를 먼저 설명하고 묻는다.
- 파일명 우선 검색은 전체 범위 확인으로 단정하지 않는다.
- truncated/unresolved와 Partial 경고를 확인하고 남은 부분은 확인 필요로 표시한다.
- 요청한 범위의 근거를 확보하면 종료한다. 범위·진행 방식 변경은 먼저 물어본다.
- 일반 조회를 위해 prepare_indexes/reload/refresh를 반복 실행하지 않는다.

보고:
단계별 파일·줄 번호와 확인한 정적 연결, 후보, 확인 필요사항을 간단히 나눠 보여준다.
시간 기록을 요청받았다면 준비·도구별 응답·원문 확인·전체 조사·최종 정리를 구분한다.
각 호출의 시각을 즉시 저장하고, 겹치는 대기를 중복 합산하지 않는다.
실패·재시도도 포함하며 미계측 값은 추정해서 채우지 않는다.

소스·설정 수정, 빌드, DB 접속, SQL 실행, 운영 반영은 하지 않는다.
```

첫 UI 결과가 없거나 동명이 많으면 화면 제목·메뉴·확인한 폴더를 이용해 후보를 좁힙니다. 범위를 바꿔야 하면 먼저 확인합니다. 요청한 분기를 생략하거나 SQL 개수를 임의로 줄여 빠르게 끝내는 규칙은 아닙니다.

| 이미 알고 있는 정보 | 시작 방법 |
|---|---|
| 화면·업무 동작 | `find_ui_actions`에 화면과 동작을 분리한 짧은 문장 |
| 메서드명·소스 파일 | 원문으로 이름 확인 후 제한한 `find_symbol`/`search_text`, 반환 ID로 후속 조회 |
| 프로시저명 | `find_sql_object`로 정의 위치, 필요하면 `analyze_procedure`로 직접 참조 |

## 수동 설치·검증

서버를 publish하려면 .NET 10 SDK가 필요합니다. 분석 대상 프로젝트의 SDK·참조 DLL·MSBuild targets는 필요하지 않습니다.

```powershell
dotnet publish src/SourceTrail.Mcp/SourceTrail.Mcp.csproj -c Release -o artifacts/server
```

publish 폴더 전체를 유지합니다. 이 README의 일괄 준비 명령을 실행한 뒤, DLL 옆 `appsettings.json`에 같은 경로 설정을 두고 서버를 시작합니다(`dotnet <publish 폴더>\SourceTrail.Mcp.dll`). 클라이언트에는 `http://127.0.0.1:3920/mcp`를 등록합니다. stdio로 쓰려면 `dotnet`과 DLL 절대 경로, `--stdio`를 등록합니다.

개발 검증은 합성 C#·WinForms·SQL fixture를 사용하며 운영 DB에 접속하지 않습니다.

```powershell
dotnet restore SourceTrail.sln
dotnet test tests/SourceTrail.Tests/SourceTrail.Tests.csproj -c Release --no-restore
```
